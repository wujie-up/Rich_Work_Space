# DeckPg 架构与性能检查（2026-10-28）

## 场景、主要矛盾与结论

场景是同时运行多个隔离插件、保留多个工作页，并持续接收 Agent 流式输出的本地工作台。主要矛盾是：为了保留工作状态和故障隔离而常驻的资源，与随历史长度、消息密度增长的复制、写盘和页面活动开销叠加。

当前宿主/业务插件分域、独立后台进程和独立站点沙箱页面的方向合理。没有证据支持为了省内存合并插件进程、关闭站点隔离或强制销毁隐藏页面。它们分别承担故障边界和未保存状态保留职责。

本次确认并修复两处不必要的瞬时内存放大：AI 会话逐事件克隆并排队写入完整历史；插件哈希校验并发读取整个包的所有文件。其余常驻内存问题列为有明确取舍的架构改进项，不以清理用户数据换取指标下降。

## 实测方法与口径

- 对正式应用只做只读进程快照和文件数量/大小统计，没有重启、更新正式应用或修改其配置、插件和历史。
- 一次进程快照为 5 个 DeckPg 进程，RSS 合计约 218 MiB；较早快照为 7 个进程、约 329 MiB。进程和用户工作状态发生变化，不能将这两个数作为优化前后对比。RSS 含共享页，求和也不是物理内存的精确值。
- 本机 AI 会话目录有 76 个文件、合计 20.222 MiB，最大约 0.785 MiB；日志目录合计约 104 MiB。磁盘体积不等于堆内存，日志体积也不代表日志全部常驻内存。
- 优化前后对比来自独立 Node 进程中的相同合成工作负载。堆数据在显式 GC 后采集；文件缓冲峰值按 1 ms 采样 `arrayBuffers`。耗时受文件缓存、调度和采样影响，不能外推成整机加速倍数。

## 已修复：流式会话持久化

位置：`plugin-dev/ai-agent/src/main/common/conversations.js` 的 `event()` / `persist()`。

原行为：每收到一个事件，立即 `structuredClone(record)`，将完整快照挂到全局写入 Promise 链。N 段输出累计复制/序列化接近 O(N²) 的历史数据。磁盘较慢时，大量完整快照同时被队列持有；单个慢文件还会阻塞其他会话写入。

现在：每个会话只保留一个待写任务；真正开始写入时才生成快照。写入期间发生更新则标记需要再次写入，合并中间快照，保留所有事件。不同会话文件独立排空；调用者仍等待本轮更新落盘，退出仍等待全部写入。写入失败向调用者传递，释放待写记录，后续可重试。保留原 JSON 格式、原子写入、事件推送和错误日志。

| 指标：600 段 × 约 1 KiB 的突发输出，写入先受阻再释放 | 原实现 | 修改后 |
| --- | ---: | ---: |
| 实际写入次数 | 600 | 1 |
| 累计 JSON 序列化量 | 194.93 MiB | 0.65 MiB |
| 排队期间额外堆占用 | 215.74 MiB | 约 0.40 MiB |
| 入队耗时 | 169.95 ms | 2.73–3.22 ms |

修改后范围来自三次复测。该场景刻意暴露队列放大；正常输出若每次写入都先完成，仍可能逐事件写入。当前完整快照格式也仍有长期写放大，本次没有引入追加日志或历史迁移。收益是消除积压时的重复快照，不能宣称常驻内存减少 99%。

验证覆盖：突发合并、写入中继续更新、最终事件一致、独立会话不互相阻塞、退出等待、并发调用者收到写入错误、失败后最新状态重试，以及既有真实文件的关闭/重开恢复。

## 已修复：插件完整性校验峰值

位置：`desk/src/main/common/plugin-package.js` 的 `fileHashes()`。

原行为：`Promise.all(readFile(...))` 同时读取全部文件。文件缓冲占用可接近整个解压包大小，且文件数量没有并发上限。启动校验、导入和打包均会经过此路径。

现在：最多 4 个工作任务，按流逐块 SHA-256；结果仍按原文件顺序返回。保留路径、符号链接、文件清单、入口和内容哈希的既有检查。

| 指标：8 个文件、总计 128 MiB 的完整性校验 | 原实现 | 修改后 |
| --- | ---: | ---: |
| 采样到的额外文件缓冲峰值 | 128.05 MiB | 30.88–31.31 MiB |
| 校验耗时 | 60.65 ms | 56.25–56.46 ms |

缓冲峰值包含已经分配但尚未被 GC 回收的块，不能理解为流的在途块大小。此处仅测校验阶段，不包含解压、磁盘复制或 Electron 启动。

验证覆盖：多块二进制文件的哈希一致、末尾内容篡改拒绝、原有符号链接/入口校验、插件安装与启用，以及原生文件选择导入 `.plg` 的隔离集成测试。

## 首轮架构发现与优先级（下述前三类已在续轮处理）

| 优先级 | 发现与代码位置 | 影响与建议 | 验收指标/取舍 |
| --- | --- | --- | --- |
| 高 | `Conversations.load()` 将全部会话正文加载进 `records`，`list()` 才排除 `events` | 历史增加会放大启动时间和常驻内存。下一阶段可将目录元数据与正文分离，按打开的会话加载正文，并为非活动正文设有界缓存 | 10 倍历史量下，未打开正文的常驻堆不随历史总字节线性增长；旧历史完整可读。需要调整同步 `read()` 及其调用契约、恢复和迁移策略，不能只删除 Map 中的数据 |
| 高 | `window-manager.js` 用 visibility/inert 保留所有已打开 iframe；`plugin-view.js` 对每个 frame 注册消息与主题监听 | 多标签有意保留 DOM、编辑状态及订阅；隐藏不等于后台挂起。可增加通用“可见/隐藏”事件，让插件暂停纯展示刷新，后台任务继续 | 多隐藏页空闲 CPU/IPC 显著下降，恢复无漏事件、无状态丢失；不能简单依靠 iframe 的 document.hidden 推断宿主标签状态 |
| 中 | 每个 frame 独立订阅宿主插件事件，过滤后向所属插件页面分发 | 宿主监听检查随页面数增加，同插件的隐藏页也继续收到事件。可建立按插件/视图订阅的分发机制 | 20 个无关页面下，单插件事件不再逐个经过无关 frame 监听；必须保留 origin/source 校验、销毁解绑和多窗口行为 |
| 中 | `codex-capture` 页面每 1.5 秒发现与刷新；`resource-monitor` 页面每秒拉取包含最多 120 个历史点的快照 | 页面隐藏/监控折叠时仍有重复传输。捕获心跳、后台采样与界面刷新应分别管理；折叠监控可只传摘要 | 折叠态传输量随历史长度保持稳定，展开历史连续；采样和连接租约不能被误停 |
| 中 | `capabilities.js` 调用记录缓存按数量限制，终态仍引用 input/result/runtime 等对象 | 已有约 512 条记录缓存和 128 个活动调用限制，不是无限增长，但条数有界不等于字节有界。可评估终态重对象释放或按字节预算淘汰 | 大查询结果完成后的内存能回落；重复读取结果及待确认/取消调用契约保持有效。先测结果保留需求，不直接删引用 |
| 中 | 宿主启动扫描校验后，激活时再次执行 `inspectPackage()`；能力审计启动扫描历史文件 | 启动 I/O 随插件和历史量增长。可评估同次启动的安装快照复用及审计索引 | 插件未变化时避免重复读取；变化/损坏仍拒绝执行。不能用“不校验”或简单 mtime 缓存削弱现有检查 |
| 低 | `conversation.js` 已增量追加消息并通过 requestAnimationFrame 合并渲染，但每轮仍扫描历史审批、按事件序号查重 | 已避免每段重建全部 DOM；长对话仍需测扫描与 DOM 规模。可用增量索引和可视区域渲染处理真正的长会话瓶颈 | 万级消息滚动与输入无明显长任务，审批状态和跳转定位正确；无需先替换整个 UI 框架 |

未发现需要推翻领域分离的证据。`PluginRuntime` 的 RPC 计时器和待响应条目在结果/退出路径中有清理；资源插件不启动后台，task 后台按完成释放；资源监控历史限制为 120 个采样点。这些已有机制应保留。本次没有执行长期堆快照分析，不能据此证明整个应用不存在内存泄漏。

## 续轮：隐藏页、历史加载和事件分发

主要矛盾仍是多插件保留工作状态与重复展示活动、历史正文常驻之间的开销；本轮覆盖宿主及 AI、资源监控、抓包、MCP、代码浏览器和工作流六个插件，没有合并进程或清理用户数据。

- 宿主通过通用可见性消息通知保留页面，并提供首次握手；页面同时遵循应用窗口的 document.hidden。共享生命周期与轮询工具停止隐藏页的展示请求，恢复时立即补刷，并防止重叠请求。业务事件仍接收，后台任务、抓包租约和资源采样继续运行。
- AI 隐藏对话暂停 DOM 渲染，恢复时使用已接收事件更新；引擎账户刷新、资源监控、抓包查看、MCP 调试展示、代码构建状态和工作流菜单展示按可见性刷新。工作流负责推进任务的 runs.resume 轮询保留，不能因隐藏中断业务。MCP 迟到的展示刷新不能产生重复轮询链。
- 资源监控收起时只传最新摘要，不传最多 120 点的历史；展开后仍可获取连续采样历史。
- AI 历史采用可重建摘要索引，正文仍保留原 JSON 格式；首次遇到旧历史需读取并建立索引，后续按文件大小和修改时间核对，仅在查看时读取正文。损坏/失效索引从原文件重建。最多缓存 8 份空闲正文，活动引擎、进行中修改和待写正文不淘汰；并发读取同一正文复用请求。后台任务、窗口绑定和任务范围调用同步适配异步读取。
- 宿主事件从每个 frame 独立监听改为一个共享监听，按插件 ID 直接分发给所属页面；保留 source/origin 校验和销毁解绑。隐藏页面继续接收业务事件，避免恢复后状态丢失。

事件测试中一个插件占 2 页，事件只投递这 2 页，不经过另外 98 页的回调。此结果代表调用次数下降，不能直接宣称整机 CPU 下降某个百分比。
