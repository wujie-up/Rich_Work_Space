# 放款巡检业务步骤展开

场景：跨财务库和国家库的定时双重核对。主要矛盾：候选未回调不等于实际仍未回调，综合节点又掩盖了筛选过程，无法判断数据在哪一步被过滤。

保留已确认SQL、status=2、只读串行分页和原payout.audit节点；新增独立步骤供本流程使用，不修改宿主、MCP和其他流程。采用原生节点之间传递结构化数据，不使用模型。

1. 先以真实引擎测试要求八个节点及完整数据链路；测试应因缺少阶段节点失败。
2. 从现有查询执行器提取共享MCP授权/取消资源管理，从collector提取财务候选与国家复核操作；原入口复用，保持旧流程行为。
3. 增加固定快照、财务候选、国家渠道分批、国家复核补merchant_no、渠道国家分组、MD保存六个节点，注册并在模板中逐步连接。输出候选数、分组批次、国家查询结果、复核明细、报告路径；仅候选节点持有完整候选事件，避免各阶段重复保存。
4. 验证101事件分页、精确大整数ID、多国家渠道、重复事件去重、0记录、不完整结果中断且不发飞书、原综合节点回归。通知使用假HTTP，不重复向实际群发送。
5. 更新流程文档，版本升至0.5.56，执行关联测试、构建和打包，交付新版JSON及plg。不修改已安装代码、用户流程或定时状态，不执行提交。

可验证指标：画布八个实际执行节点；每个节点具有独立状态和输出；查询错误定位到具体步骤并阻止通知；SQL边界及最终MD与旧流程一致；模型调用数0。

追加用户要求：MD和飞书表格仅保留申请单ID、创建时间、merchant_no，删除正文查询追溯；飞书改原生表格卡片，保留后台查询记录。验证卡片签名、大小和分段全量性，不重复发送真实消息。
