# 软件研发七阶段工作流

提供两种使用方式：完整流水线自动衔接七阶段；独立阶段按需导入，通过产物文件衔接。两者共用角色、提示词和评审标准，可对同一需求分别运行比较。

两种方式均支持阶段独立运行和资料接续。本次补齐评审的分析、修改、校验闭环，配合 work-flow 0.5.42 的可选循环限制；不改动已安装的模板、历史和运行快照。

## 导入与开始

在工作流插件选择“导入”，从 `exports/` 选择 JSON，导入方式保留“新建工作流”。需要更新已有流程时，选择更新目标并确认；原运行历史及暂停快照保留，暂停运行继续使用当时的定义。

| 文件 | 使用方式 |
|---|---|
| [00 完整流水线](exports/00-full-pipeline.workflow.json) | 七阶段自动接续；测试失败自动修复并复测 |
| [01 需求评审](exports/01-requirements.workflow.json) | 产品编写，产品／研发／测试并行评审 |
| [02 研发方案设计与评审](exports/02-design.workflow.json) | 研发结合代码与设计 skill 编写，三角色并行评审 |
| [03 测试用例编写与评审](exports/03-test-cases.workflow.json) | 测试结合代码与用例 skill 编写，三角色并行评审 |
| [04 代码实施与评审](exports/04-implementation.workflow.json) | 研发实际编码，研发／架构并行评审，不通过则修订 |
| [05 测试验证](exports/05-verification.workflow.json) | 独立执行页面集成测试，输出缺陷报告 |
| [06 缺陷修复](exports/06-bug-fix.workflow.json) | 独立按报告修复实际代码，输出修复记录 |
| [07 验收](exports/07-acceptance.workflow.json) | 产品验证页面和后台数据，输出验收报告 |
| [08 测试与修复联跑](exports/08-verification-fix-loop.workflow.json) | 阶段 5→6→5 循环，供独立阶段组合使用 |

运行开始时有两次集中输入，无需编辑后续节点：

1. 选择主文档（工作台文件、系统文件或粘贴链接）。需求评审和完整版选需求；阶段 6 选缺陷报告；其他阶段选需求分析。
2. 在“本次项目与补充资料”填写 JSON；文档字段支持正文、文件路径或链接。已有资料填入，允许本阶段创建的文档可留空。必需资料不足时由协调 Agent 提出具体问题。

完整流水线示例（路径请替换为实际项目和本次任务目录）：

```json
{
  "projectDirectory": "/absolute/path/project",
  "outputDirectory": "/absolute/path/review-runs/task-001",
  "requirements": "",
  "analysis": "",
  "design": "",
  "cases": "",
  "defects": "",
  "testEnvironment": "测试地址、启动方法、可用账号与数据权限说明；不填写密钥",
  "constraints": "本次需求边界和已确认决定",
  "allowedFiles": ""
}
```

独立阶段启动输入：

| 阶段 | 必需输入 | 可选的上一版输入 |
|---|---|---|
| 1 | 需求正文／可读链接 | `analysis` |
| 2 | `analysis`、项目目录 | `design` |
| 3 | `analysis`、项目目录 | `cases` |
| 4 | `analysis`、`design`、项目目录、精确修改文件范围 | 本次已有改动由 Agent 读取 |
| 5 | `analysis`、`cases`、项目目录、测试环境 | `defects` |
| 6 | `analysis`、`design`、`defects`、项目目录、精确修改文件范围 | 缺陷报告中附上轮修复记录 |
| 7 | `analysis`、项目目录、页面与后台数据核验环境 | 分析附件中的测试证据 |
| 08 | 阶段 5 与 6 的输入集合 | 上轮缺陷／修复记录 |

完整版的分析、设计、用例由前序自动接续，不要求启动时全部准备好。项目目录可写在需求中由协调 Agent 提取；输出目录需明确提供。独立阶段例如先运行 01，再把输出的 `01-需求分析文档.md` 作为 02／03 的主文档；运行 04 时还需在 `design` 填入 02 的输出路径。05 和 06 只执行各自阶段，需要自动复测时使用 08。

## 评审与循环

前三阶段由作者提交完整文档和稳定编号的原子检查项，再由产品、研发、测试分别评审。各角色认可率按 `floor(认可项 / 适用检查项 × 100)` 计算，**每个角色均 ≥90%，没有阻断及未决问题**才放行。前三阶段只评文档是否足以进入下一阶段，后续运行验收项完整保留为 `futureAcceptance`，不混入本阶段评分；实施、测试和验收仍要求真实执行证据。下一轮保留当前完整产物、全部意见、缺陷／修复记录和已确认答复，禁止删掉失败项提高分数。

问题使用稳定编号。作者在 `resolutions` 中逐项记录修改位置、验证步骤和证据；各角色独立核对，协调 Agent 仅将有修改及复核证据的旧问题加入累积 `resolvedIssueIds`。文字重排、同义改写、作者自行声明完成，都不能作为关闭问题的依据。

比例和证据一致性由评审 Agent 与汇总 Agent 复核；条件节点另行检查整数比例、阻断与问题字段。现有节点不做确定性的逐项数学证明，因此结果仍需要结合实际证据判断。验收阶段要求全部验收项满足（100%），不会因前序达到 90% 自动通过。

每个评审环节总计最多 **5 轮**，不是可追加的批次。第 5 轮通过可正常放行；仍未通过则保存并暂停，不能追加第 6 轮。首次完整评审作为基线，之后连续 **2 轮**没有新增已验证关闭的问题，提前保存并暂停；人工检查修改及校验证据后可选择继续，但仍受总计 5 轮限制。退出写入“未完成”，不继续后续阶段。到达总上限需调整资料或流程后新建运行，原结果保留。常规修订自动进行，用户仅处理无法从文档、代码或已确认决定中解决的取舍、范围／权限或环境问题。关闭问题弹窗或稍后处理沿用现有中断、保存和继续机制。

测试与修复联跑由测试和研发分别核验，共同达标后才退出循环。代码任务串行执行，只读评审并行执行。

## 输出与运行条件

各阶段输出 `01-需求分析文档.md`、`02-需求设计方案.md`、`03-用例分析文档.md`、`04-代码实施报告.md`、`05-测试缺陷报告.md`、`06-缺陷修复报告.md`、`07-验收报告.md`，保存完整正文；状态见流程结论及审查记录。`audit/` 中分别保存作者原始输出（含决定、检查项和证据）、全员评审、协调结论 JSON，保留最近一轮已完成记录；运行中断时部分记录可能尚未生成。没有进入的修复阶段不会生成修复报告。暂停时，当前输出、上一轮完整上下文及检查点保存在插件原有运行存储中；历史列表沿用插件的摘要和数量限制。

作者正文使用 `artifact: ["完整 Markdown"]`，通过现有输入映射和整个数组引用传递，保留空行，避免把文档中的 `{{变量}}` 再次解释成工作流变量。Markdown 文件仅包含正文；是否通过请查看流程结论与审查记录。跨阶段自动传递已确认决定；独立阶段的作者也被要求将决定和检查项写入正文，便于只通过导出文档衔接。

输出目录请使用每次任务新建的独立目录，**同名阶段文件会覆盖**；不得设成输入原文件路径。实际业务代码留在项目目录，报告只记录改动及证据。阶段 4／6 的代码范围沿用现有 1–30 个精确相对路径限制，完整版由设计阶段给出；超出范围先询问用户。页面验证只授权写 `.deckpg/test-evidence.md`、`.deckpg/acceptance-evidence.md`，不授权测试 Agent 修改业务代码。

需要现有工作流插件的导入／导出、并行／汇合、循环、用户介入、中断续跑及 Agent 结构化输出能力；新限制要求 work-flow **0.5.42 或更高版本**。循环节点新增总轮数、无进展轮数和问题编号输入，默认不启用，旧定义继续沿用原有批次行为。更新模板后必须新建运行，旧运行仍使用原快照。AI Agent 提供方需已启用并具备实际文档／代码读取能力。链接由输入节点原样传递，后续 Agent 按可用工具读取；无法读取时请求正文，不猜测内容。

需求分析、方案设计和用例编写会核对实际可用 skill 并记录路径；缺少技能时由用户决定补充或明确同意不用技能继续。页面测试和验收还需要 Agent 可用的浏览器、接口及后台数据工具、测试地址、登录和数据权限。工具缺失时暂停询问，单元测试及代码阅读不能替代真实页面／后台验收。

## 生成与验证

在仓库根目录执行：

```sh
node docs/workflows/software-development/generate.mjs
node --test docs/workflows/software-development/*.test.mjs
```

生成脚本只写本目录的九份导出文件，先使用现有导入校验器检查全套定义。验证结果及未验证范围见 [verification.md](verification.md)。可在插件内修改导入后的节点并再次导出，日常调整模板无需升级插件。
