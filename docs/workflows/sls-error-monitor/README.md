# 新老系统 ERROR · 半小时巡检

导入文件：[sls-error-monitor.workflow.json](./sls-error-monitor.workflow.json)。源码为 `workflow.mjs`。

本版需要工作流 **0.5.46 或以上**，包含连续时间窗、规则查询、关键日志附录及不覆盖的时间后缀报告。新建流程时导入本文件；已有巡检流程仅为此次命名调整升级插件即可。以后调整范围、过滤规则或流程内容，只需编辑节点或重新导入，不需要再次升级插件。升级保留原模板和运行历史。

## 运行范围

老系统 16 国、50 个 Logstore，新系统 7 个 Logstore。按地域及项目分为七组并行查询，等待全部结果后统一去重、分类、定位根因并输出处理方案。所有生产操作只读；方案不会自动执行。

使用已安装的 `ai-agent-sessions` 与既有 `sls-br-appserver` MCP 服务；定义中不包含凭据。各库名称已通过实际 SLS 库清单核对。

## 维护过滤规则

选择“过滤规则 · 生成 SLS 查询”节点，在右侧“已确认过滤规则 JSON”中维护规则数组。初始为空，不擅自排除任何异常。每条规则必须具有唯一 ID、启用状态、确认依据、适用范围和非空条件。

以下为**停用的格式示例**；启用前应替换成已经确认可排除的真实业务异常：

```json
[
  {
    "id": "business-example",
    "enabled": false,
    "reason": "填写业务方确认依据及日期",
    "scope": { "system": "old", "country": "br", "project": "ai-br", "logstore": "app" },
    "conditions": [
      { "field": "location", "operator": "equals", "value": "填写确认的错误位置" },
      { "field": "message", "operator": "contains", "value": "填写确认的业务异常固定片段" }
    ]
  }
]
```

- `scope` 支持 system、country、region、project、logstore；省略的字段不限制，空对象表示全部目标。
- 条件字段支持 message、location；比较方式支持 contains、equals。多条件同时匹配才排除，多规则任一匹配即可排除；多个规则重叠的日志不重复计数。
- 停用规则使用 `enabled:false`，删除规则则移除对应项。保存工作流后，下次运行使用新规则；当前运行仍使用自己的配置快照。
- 节点确定性生成每个日志库的计数、聚合和样本 SQL，过滤在 SLS 查询内执行；可在节点结果中查看语句与适用规则。Agent 不自行生成永久排除规则。

## 关键日志及 Markdown 格式

更新本目录工作流，并使用 work-flow **0.5.45 或以上**。查询节点为每类问题保留 1–3 条真实脱敏日志，包含来源系统、国家、地域、项目、日志库、
`location`、`message` 及实际取得的时间/请求标识；未取得的字段不推测，无本轮样本则明确写出原因。

保存报告节点直接从各查询分支追加“关键日志与过滤定位”，按 P0 至 P3 排列，不依赖分类或分析 Agent 再次复述日志。
日志使用 JSON 代码块保留字段和值，可将 `location`、`message` 中稳定且非敏感的片段用于已有过滤规则；
不要复制动态编号、脱敏占位符或截断标记作为规则，确认前不会自动排除。样本条数与异常总量分别说明。

报告标签统一使用 `- **处理**：正文`，修正中文冒号位于加粗标记内部导致星号原样显示的问题；修正仅针对证据/根因/处理/验证标签，代码块不改写。
新报告桌面文件与归档仍保持一致。历史报告及已启动运行的流程快照不会自动改写。

从导入入口选择“更新已有工作流”，保留原模板、历史及状态数据；如已维护过滤规则，请先导出备份并将其保留到新版规则节点，
不要用模板默认的空数组覆盖。导入后按原有规则重新启用每 30 分钟定时执行。

## 筛选口径

只查询 `level: ERROR`。每库统计原始 ERROR、规则排除及保留数量，再聚合保留的错误并按需取样；记录是否 Complete、失败原因、实际语句及 request ID。任何失败、缺失、截断或未知结果都必须在报告中显示，不能视为无异常。

同类问题合并，仍保留国家、服务和本窗口次数；持续故障不会因上轮出现过就隐藏。看起来符合预期但未经确认的异常进入“待核实”，避免误屏蔽数据问题。

## 调度与恢复

导入协议会将运行方式设为手动。导入或更新后需设置“固定周期 / 每 30 分 / 启用自动触发”，然后保存。首次可手动运行。读取排期或保存无关流程不会延后已排定的触发时间，修改触发规则才重新排期。

**关闭最后一个工作流窗口后停止巡检，不在后台继续。** 最小化保留运行。DeckPg 退出、插件禁用或系统休眠时也无法查询。上一轮未结束时不会重叠启动下一轮。

每轮固定查询区间为 **[上次成功查询结束秒，本轮时间窗节点执行时的当前秒)**，所有日志库共享。首次无历史时查最近 30 分钟，不做半小时取整、2 分钟延迟或重叠。关闭后重新打开，下次运行从保存游标接续；不截断为最近 24 小时，也不回放多次调度。

若上一轮查询不完整，从其未完成起点重查到新的当前时间，不静默跳过失败窗口。旧版摘要明确成功才采用其 windowTo，否则从 windowFrom 重查；状态损坏明确报错，不默认为首次。已知五个缺少 level 索引的库仍会阻止成功水位推进；必须单独解决索引或覆盖问题，不能通过规则掩盖。
