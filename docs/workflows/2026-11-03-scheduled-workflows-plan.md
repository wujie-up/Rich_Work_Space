# 定时工作流实施计划

**场景与主要矛盾：** 定时工作流跨插件生命周期执行，而当前排期仅存于内存，用户无法区分等待与运行，重启会丢失应执行时间。

**目标：** 图标区分定时启用与实际运行，提供立即触发入口，保存每个工作流最近执行时间、情况和下次排期，启动后补跑到期未执行任务。

**架构：** 仅修改 `plugin-dev/work-flow`。复用插件 JSON 存储、运行引擎和运行事件，不新增数据库依赖或宿主业务逻辑。定时执行表独立于用户编辑的工作流定义；关联运行 ID 判断已启动任务，防止重启重复提交。多次漏跑合并一次；已经启动的中断运行沿用人工续跑。

**范围：** 新增定时执行表模块与测试；修改 triggers.js、index.js、工作流列表与运行方式 UI、直接相关测试、README 和插件版本。不得提交、安装或发布；保留工作区现有改动。

## 实施步骤

- [x] 1. 编写并运行失败测试：持久化排期，未来任务重启不重置，周期/每日/单次任务漏跑补一次，执行结果持久化、失败隔离、禁用/配置变更、停止时在途读写不恢复定时器。
- [x] 2. 实现定时执行表和调度恢复，接入运行事件与立即触发 RPC。表记录工作流 ID、配置、下次时间、最近运行 ID、开始/结束时间、状态、错误及触发来源。立即触发不消费原定时排期，执行中拒绝重复启动。
- [x] 3. 编写并运行界面失败测试；列表同时容纳既有运行图标和独立时钟标识；顶部运行操作组增加立即触发图标按钮（title 与 aria-label 一致），复用公共控件。展示最近执行时间与情况。
- [x] 4. 运行定时、工作流入口及直接关联测试，明暗主题、窄窗口、键盘焦点与禁用状态界面验证；更新版本、构建并校验 .plg，不运行其他领域全量测试。

## 验证重点

- 重启时已到期但未执行的任务立即执行一次；再次重启不重复消费单次任务。
- 运行事件比启动接口返回更快时，执行表仍保留最终结果。
- 多工作流并发更新不互相覆盖；记录失败不影响原运行和运行事件。
- 禁用、删除、修改配置及停止期间的异步回调不恢复旧排期。
- 手动触发成功或失败均不改变原排期；忙碌时不会启动第二个实例。

执行方式：当前会话直接实施，不提交。该计划落实用户已确认的三项要求。
